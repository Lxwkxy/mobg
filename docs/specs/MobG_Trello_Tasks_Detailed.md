| ส่วน | ใช้ | เจ้าของหลัก |
|---|---|---|

| สิทธิ์โปรเจกต์และงาน | middleware/service ของ MobG อ่าน Better Auth session และข้อมูล Owner/Member | Book เรียก DB functions ของ Pai |

**การเชื่อมระบบ:** Next.js → Express API/Better Auth handler → PostgreSQL  
Next.js เป็นหน้าเว็บ Express เป็น API/auth server หลัก และ Docker รันฐานข้อมูล PostgreSQL ส่วนเว็บ/API รันบนเครื่องพัฒนาได้

Better Auth เชื่อม Express ผ่าน handler และอ่าน session ใน API ได้ ส่วน client ใช้กับ React ของ Next.js ได้ จึงไม่ต้องทำระบบตรวจรหัสผ่าน/session อีกชุด [Express integration](https://www.better-auth.com/docs/integrations/express), [Auth client](https://www.better-auth.com/docs/concepts/client)

PostgreSQL ใช้ schema ธุรกิจเดิมต่อ และเพิ่ม/mapping auth schema ให้ตรง configuration ผ่านวิธีของ Better Auth ต้องตรวจ SQL และการชนตารางก่อน migration [PostgreSQL adapter](https://www.better-auth.com/docs/adapters/postgresql), [Auth database](https://www.better-auth.com/docs/concepts/database)

## Flow ผู้ใช้และขอบเขตบัญชี
เปิดเว็บ → ตรวจ Better Auth session → Login ด้วย email/password หากไม่มี session → Dashboard → ใช้งานตามสิทธิ์ → Logout กลับ Login
- รอบนี้มี Login/Logout/session/สิทธิ์และบัญชีสาธิตที่ทีมเตรียมให้ ไม่มี UI สมัครสมาชิก ลืมรหัสผ่าน หรือโปรไฟล์ใหม่
- ขั้นตอนเตรียมบัญชีใช้ server API ที่ Better Auth รองรับ เช่น signUpEmail จากสคริปต์ภายใน ไม่ใช้การ insert password hash เอง [Email & Password](https://www.better-auth.com/docs/authentication/email-password)
- Book/Pai แยกขั้นตอน seed ที่อนุญาตให้สร้างบัญชีจาก configuration ของ server ที่ใช้จริง ซึ่งต้องจำกัด signup สาธารณะตามขอบเขต; การซ่อนหน้าสมัครสมาชิกอย่างเดียวไม่พอ
- การตรวจ cookie/session ใช้ Better Auth ส่วน Owner/Member และสิทธิ์อ่าน/แก้/ลบงาน ตรวจด้วย Express API และความสัมพันธ์ใน PostgreSQL
- ผู้สร้างเข้าถึงโปรเจกต์ใหม่ได้ทันที My Tasks ใช้ user id จาก session และ Dashboard/รายการใช้ขอบเขตสิทธิ์เดียวกัน
- session หมดอายุให้กลับ Login และล้างข้อมูลบัญชีเดิม; Login แล้วแต่ไม่มีสิทธิ์ให้เห็นข้อความพร้อมทางกลับ

## ทำงานพร้อมกันและจุดส่งต่อ
**ID ที่ใช้ต่อจาก W1:** Better Auth user.id เป็น string; Book เรียก profile lookup ผ่าน users.auth_user_id เพื่อได้ users.user_id ตัวเลขของ MobG ก่อนตรวจสมาชิกหรือเรียก DB functions

- Bar ทำ UI/mock ตาม contract Book ร่าง Express routes/types/config และ Pai ตรวจ PostgreSQL/schema/DB functions พร้อมกันได้
- **รหัสการ์ดอ้างอิงหมายถึงส่วนที่จำเป็น ไม่ต้องรอทั้งการ์ด Done** ส่ง config/function/endpoint เมื่อส่วนนั้นพร้อม แล้วเพื่อนเชื่อมต่อทันที
- ต้น W2 ใช้ config/client/schema/types จาก W1 ต่อ; Pai ส่ง profile/membership functions และบัญชีจริงให้ Book/Bar แล้ว Book ส่ง guard กับ /api/me
- Pai เตรียมบัญชีผ่าน Better Auth แล้วส่ง user id จริงและบัญชีสาธิต; Book/Bar เชื่อม Login จริงหลัง config/schema/บัญชีพร้อม
- config ตัวอย่างและ mapping คุยตั้งแต่ W1 จึงไม่รอ auth server ทั้งชุดก่อนเริ่ม UI หรือฟังก์ชันสมาชิก
- API/DB อ่านรายชื่อผู้รับผิดชอบพร้อมใน W2 ส่วน UI เพิ่ม/นำสมาชิกออกอยู่ W4
- TypeScript ช่วยกำหนดข้อมูล แต่ Book ยังต้อง runtime validate request และ Pai ยังต้องใช้ foreign keys/parameter query
- เมื่อเปลี่ยน contract/types/auth config/schema หรือ component ร่วม ให้แจ้งเจ้าของส่วนที่ใช้ต่อ

## กำหนดส่งและ Trello
- คัดลอกชื่อการ์ด/Description และใช้หัวข้อย่อยเป็น Checklist ไม่สร้างหัวข้อย่อยเป็นการ์ดใหม่
- การ์ด W1–W5 ส่งวันสุดท้ายของสัปดาห์นั้น ยังไม่มีวันที่เริ่ม/วันส่งจริงจึงไม่กำหนดวันที่ปฏิทิน
- R วางใต้ Book/Pai ในไฟล์นี้ เริ่มทำใน W4 และส่งวันสุดท้าย W4 ก่อนตรวจรวม W5; ตอน W2 ลงเฉพาะหกการ์ดหลัก
- ใช้ Label เจ้าของ + สัปดาห์ หรือ Responsive และ List เช่น Backlog, Doing, รอเชื่อม, Review, Done
- เกณฑ์ Done คือครบผลงานทั้งการ์ด แต่ comment แจ้งส่วนที่พร้อมได้ก่อน และระบุสิ่งที่ยังรอชัดเจน
- ทุกคนตรวจส่วนตัวเองก่อนส่ง Pai เน้นความถูกต้องข้อมูล/การเชื่อมถึง DB ไม่ใช่ผู้ตรวจแทนทุกส่วน

#### W2-Bar-01 เชื่อม Login ตรวจสถานะผู้ใช้และทำ Logout

**Description**

**Checklist**

- ใช้ auth client เดิม ตั้ง URL ของ Express ผ่าน env ฝั่งเว็บ และส่ง cookie ด้วย `credentials: "include"`
- เปลี่ยนปุ่ม Log in ให้เรียก `authClient.signIn.email` ด้วย email/password จากฟอร์ม; คง loading ป้องกันกดซ้ำ และแสดง error จากผลจริง
- เมื่อ Login สำเร็จ เรียก `GET /api/me`; ใช้ `{ userId, userName, email }` จาก Book แสดงใน Topbar และใช้กับหน้าอื่น
- อ่าน session ด้วย `getSession/useSession` เมื่อเปิดหรือรีเฟรชหน้าภายใน รอผลก่อนแสดงข้อมูลของบัญชี

- เปลี่ยน Logout ให้เรียก `authClient.signOut`; เมื่อสำเร็จล้างข้อมูลผู้ใช้และรายการที่ค้าง แล้วกลับหน้า Login
- ถ้า Logout ล้มเหลว ให้แสดง error และปุ่มลองใหม่ โดยไม่แสดงว่าออกจากระบบสำเร็จ

- ตรวจ Login ถูก/ผิด รีเฟรช URL ภายในโดยตรง session หมดอายุ Logout และเปลี่ยนบัญชี โดยใช้บัญชีจริงที่ Pai เตรียม

- เรียก `findDomainUserByAuthId(session.user.id)` ของ Pai เพื่อหา `users.user_id`; คง Auth ID เป็น string และแปลงเฉพาะ MobG ID หลังตรวจ positive safe integer
- ทำ guard แนบโปรไฟล์/ตัวตนที่ตรวจแล้วให้ request ภายใน; ตัวตนและ role ต้องมาจาก Backend
- ทำ `GET /api/me` คืน `{ success: true, user: { userId, userName, email } }` จากโปรไฟล์ MobG โดยไม่คืน credential/token
- ไม่มี/หมดอายุ session ให้ตอบ `401 UNAUTHENTICATED`; มี session แต่ไม่มีโปรไฟล์ที่ผูกไว้ให้ตอบ `403 FORBIDDEN`
- ทำ guard สมาชิกด้วย `findProjectMembership(projectId, userId)`; ไม่เป็นสมาชิก/ไม่มีโปรเจกต์ตอบ `404` และสิทธิ์ Owner ไม่พอตอบ `403`
- ใส่ guard ใน API โปรเจกต์ของ W2 และเขียนวิธีใช้ต่อกับ API งานใน W3; role ที่ไม่รู้จักต้องไม่ได้สิทธิ์
- ตรวจ API ตรงก่อน/หลัง Logout, session หมดอายุ, Owner/Member และบัญชีที่ไม่เป็นสมาชิก
- คง signup สาธารณะปิดไว้ ใช้ seed process แยกตามคู่มือ W1 สำหรับสร้างบัญชีเท่านั้น
- ส่ง `/api/me` รูปแบบ error และ URL ให้ Bar ทันทีที่ใช้ได้ พร้อมบันทึกวิธีใช้ guard ให้ทีม

**เริ่มได้เมื่อ / ส่วนที่ทำก่อนได้**

เขียนโครง guard และ `/api/me` จาก interface W1; เชื่อมจริงเมื่อ Pai ส่ง profile/membership functions และบัญชี

**ถือว่าเสร็จเมื่อ**

- ไม่มี session/หมดอายุ/Logout แล้วเข้า API ภายในไม่ได้
- guard ตรวจสมาชิกและ Owner ได้ พร้อมวิธีใช้ต่อใน W3
