# MobG API Contract

See the [schema mapping](../database/schema-mapping.md) for database storage
and relationships.

## 0. Running the Backend

Follow [README.md](README.md). From backend: npm ci, then npm run dev.
For compiled execution: npm run build, then npm start.
The shared pool is src/db.ts and the connection command is npm run check-db.

- API origin: BETTER_AUTH_URL, default http://localhost:5000.
- Web origin: CORS_ORIGIN, default http://localhost:3000.
- BETTER_AUTH_SECRET: private random secret of at least 32 characters in root .env.
- Frontend sends credentials: 'include'. The React client is web/lib/auth-client.ts.
- GET /api/health checks the server only; it does not verify authentication or the DB.
- Apply migrations 001-007 before starting the API. No migration runs at server startup.

## 1. Login / Logout / Current User

Better Auth owns /api/auth. Use its client methods and native response/error shapes;
the business envelope in section 9 does not apply to these routes.

| Endpoint | Client method | Result |
|---|---|---|
| POST /api/auth/sign-in/email | authClient.signIn.email({ email, password }) | Native Better Auth user/token result and session cookie |
| GET /api/auth/get-session | authClient.getSession() / useSession() | Native { session, user }, or null when no session |
| POST /api/auth/sign-out | authClient.signOut() | Native success result; library clears the cookie |
| POST /api/auth/sign-up/email | authClient.signUp.email({ name, email, password, callbackURL }) | Creates a public account and MobG profile; sends verification mail; no session |
| POST /api/auth/send-verification-email | authClient.sendVerificationEmail({ email, callbackURL }) | Resends verification mail when needed |
| GET /api/auth/verify-email | Link generated by Better Auth | Verifies the signed email token; frontend callback |
| POST /api/auth/request-password-reset | authClient.requestPasswordReset({ email, redirectTo }) | Generic response whether or not the email exists |
| POST /api/auth/reset-password | authClient.resetPassword({ token, newPassword }) | Spends token, replaces password and revokes sessions |
| GET /api/me | Business API | { success: true, user: { userId, userName, email } } |

Example flow with curl in PowerShell (Windows PowerShell 5.1 and PowerShell 7). Use `curl.exe`,
not the `curl` alias. The password is typed into a hidden prompt and never appears on the command
line or in history. JSON bodies are built with `ConvertTo-Json` and sent to curl through stdin
(`--data-binary '@-'`), so no quote escaping is needed: hand-escaped `\"` inside a PowerShell
argument reaches the server as a literal backslash on PowerShell 7.3+ and breaks the JSON.
Better Auth checks `Origin` on POST, so send the web origin:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)   # pipe UTF-8 (5.1 defaults to ASCII)
$o = 'http://localhost:3000'; $api = 'http://localhost:5000'

$ownerEmail = 'demo-member@example.test' # Use the seeded Owner's email if different.
$secure = Read-Host "Password for $ownerEmail" -AsSecureString
@{ email = $ownerEmail; password = [System.Net.NetworkCredential]::new('', $secure).Password } |
  ConvertTo-Json -Compress |
  curl.exe -s -c cookies.txt -H "Origin: $o" -H 'Content-Type: application/json' --data-binary '@-' "$api/api/auth/sign-in/email"
Remove-Variable secure

curl.exe -s -b cookies.txt "$api/api/me"                    # 200 { success, user: { userId, userName, email } }
curl.exe -s -b cookies.txt "$api/api/projects?status=In%20progress"

# Find the IDs instead of guessing them: they differ in every database.
$projectId = ((curl.exe -s -b cookies.txt "$api/api/projects" | ConvertFrom-Json).projects |
  Where-Object projectName -eq 'MobG W5 Main Demo').projectId
$taskId = ((curl.exe -s -b cookies.txt "$api/api/projects/$projectId/tasks" | ConvertFrom-Json).tasks |
  Where-Object taskTitle -eq 'Future Medium').taskId
"projectId=$projectId taskId=$taskId"                        # both must be numbers before the PATCH

@{ status = 'Done' } | ConvertTo-Json -Compress |
  curl.exe -s -b cookies.txt -X PATCH -H 'Content-Type: application/json' --data-binary '@-' `
    "$api/api/projects/$projectId/tasks/$taskId"            # 200 { success, task }

curl.exe -s -b cookies.txt -X POST -H "Origin: $o" -H 'Content-Type: application/json' -d '{}' "$api/api/auth/sign-out"
curl.exe -s -b cookies.txt "$api/api/me"                    # 401 UNAUTHENTICATED
Remove-Item cookies.txt
```

The old /api/auth/login, /me and /logout routes are retired.
Auth users have string IDs. Business userId is a numeric MobG ID obtained through
users.auth_user_id after the server validates the Better Auth session.
Do not cast auth.user.id to a number or trust a localStorage identity.
GET /api/me and business guards return 401 UNAUTHENTICATED for no usable session,
403 FORBIDDEN for a session without a linked domain user, and 500 for database failures.
No password, credential hash or token may be included in the business user profile.

Public signup is enabled by the user's additional account-feature scope. Names are trimmed
and limited to 1–100 characters; email is trimmed/lowercased and limited to 255 characters.
Passwords use Better Auth's 8–128 character limits and are never trimmed or lowercased.
Public accounts must verify email before session creation (403 EMAIL_NOT_VERIFIED).
Verification links expire after one hour; reset links expire after 30 minutes and are single-use.
Callbacks/redirects must use CORS_ORIGIN. Registration creates no project memberships.
Migration 007 creates the MobG profile inside the signup transaction. Existing profiles are
never claimed by email, and client-supplied verification/registration-kind fields are not trusted.
Trusted provisioned accounts retain their existing login behavior and explicit profile-link workflow.
See [account registration](../docs/account-registration.md) for mail setup and this compatibility policy.
Never trim or lowercase passwords. Better Auth owns credential validation and errors;
the frontend displays a generic login error and handles network errors separately.

## 2. Sessions

Better Auth handles session creation, validation, renewal, cookies and sign-out.
The configured lifetime is seven days; cookie cache is disabled so authorization
reads database session state. Keep the library's HttpOnly/SameSite/Secure defaults.
Use auth.api.getSession({ headers: fromNodeHeaders(req.headers) }) on Express.
Session user.id refers to auth_users.id; resolve the MobG profile before checking roles.

Migration 005 creates auth_sessions. Its token has Better Auth semantics, not the
SHA-256 token_hash contract of legacy sessions. Do not copy or convert legacy sessions.
Migration 004 defines the legacy session table. Better Auth uses `auth_sessions`.
The API enforces Owner/Member permissions using project membership.

Session outcomes

| Situation | Business API (`/api/me`, `/api/projects`, ...) | Web app |
|---|---|---|
| No cookie, forged cookie | `401 UNAUTHENTICATED` | Protected pages go to `/login` |
| Session past `expires_at` (7 days; Better Auth extends it on use after one day, its `updateAge` default) | `401 UNAUTHENTICATED`; a write with an expired session changes nothing | Same as no cookie |
| After `POST /api/auth/sign-out` | The old cookie gets `401` on every business route | Logout button signs out, then `/api/me` 401 → `/login` |
| Valid session, auth user not linked to `users.auth_user_id` | `403 FORBIDDEN` "No MobG profile is linked to this account" | Error state |

Server pieces: `src/auth.ts` (Better Auth config: `basePath /api/auth`, `trustedOrigins [CORS_ORIGIN]`,
DB session tables from migration 005, rate limits, email verification/reset hooks),
`src/middleware/auth.ts` (`requireAuth`, `requireProjectRole`), `src/guards.ts` (wires them to the DB).
Client: `web/lib/auth-client.ts` (`createAuthClient({ baseURL: NEXT_PUBLIC_AUTH_URL, basePath: '/api/auth', fetchOptions: { credentials: 'include' } })`);
business fetches also send `credentials: 'include'`.

Better Auth errors use its native shape `{ "code": "...", "message": "..." }`, not the section 9 envelope:

| Request | Status / `code` |
|---|---|
| Sign-in, wrong password or unknown email (same answer) | `401 INVALID_EMAIL_OR_PASSWORD` |
| Sign-in, public account not verified | `403 EMAIL_NOT_VERIFIED` |
| `callbackURL` / `redirectTo` outside `CORS_ORIGIN` | `403 INVALID_CALLBACK_URL` |
| Sign-up name/email invalid | `400 INVALID_REGISTRATION` |
| Sign-up, reset or resend while SMTP is not configured | `503 ACCOUNT_EMAIL_UNAVAILABLE` |
| Too many requests (sign-in 30/min, sign-up 15/min, resend/reset 5/min per IP) | `429` |

## 3. Passwords and Account Provisioning

See [account provisioning and recovery](../database/README.md#provision-or-recover-a-single-account) for setup and inputs.

Short version: accounts that can log in are made only through Better Auth's server API, never by SQL.
`src/provisioning/accounts.ts` builds `seedAuth` (the same config with `registrationKind: "provisioned"`,
no verification mail) and `provisionAccount()` calls `seedAuth.api.signUpEmail` and links the new auth
user to an existing or new `users` row in one step. Ways to run it:

| Need | Command (from `backend/`, passwords set privately in the terminal, never on the command line) |
|---|---|
| Link one existing MobG user or create one new profile | `npm run seed:accounts -- --database NAME` with `SEED_DOMAIN_USER_ID` or `SEED_NAME`/`SEED_EMAIL`, plus `SEED_PASSWORD` |
| Owner + Member + Outsider and the W5 demo projects | `. ./scripts/set-seed-env.ps1`, then `npm run seed:demo -- --database <mobg_w5_demo_*> --w5` |
| Disposable accounts for an automated check | `npm run test:api-audit` / `npm run test:demo-rehearsal` (passwords live only in memory) |

Use Better Auth's default password implementation. Credentials live in
auth_accounts.password with provider_id = credential, not users.password_hash.
The legacy password_hash column remains for existing data but is nullable after 005.

The SQL demo seed is domain data only and cannot log in.
The seeding CLI uses a separate Better Auth instance. Provisioned accounts
skip the verification email step. Capture the actual auth ID and explicitly link the intended domain row.
Do not copy bcrypt/placeholder hashes into auth_accounts, print credentials, silently
merge accounts by email, or create a second domain profile for the existing demo user.
Profile name/email come from users for business responses; provisioning must reconcile
them with the intended auth account and preserve the existing project owner identity.

## 4. Core Database Contracts

| Function | Input | Result |
|---|---|---|
| findDomainUserByAuthId(authUserId) | String ID from a validated Better Auth session | { user_id: string, user_name, email, auth_user_id } or null |
| findProjectMembership(project_id, user_id) | Positive safe integer project ID and linked MobG user ID | { project_id: string, user_id: string, role } or null |

DB interface types are in src/services/authDb.ts and src/services/projectDb.ts.
Canonical business request/response DTOs are in src/contracts/api.ts; Frontend
re-exports them through web/types/index.ts.
Database failures propagate; null means no matching row.
Unknown roles grant no permission. The membership lookup cannot distinguish an
unknown project from a nonmember; both are denied by the business guard.

- pg BIGINT results remain decimal strings; do not change the global parser.
- Convert a domain ID only after full decimal validation and Number.isSafeInteger(id) && id > 0.
- Validate incoming IDs in full; 1abc is invalid. Invalid request IDs return 400.
- A stored domain ID outside the safe integer range is 500, never a rounded ID.
- Auth IDs remain strings and must only be used to look up users.auth_user_id.
- The user ID for database writes comes from the validated session and its link,
  never from a client identity claim.

## 5. Permission Matrix (Roles: `Owner` vs `Member`)

| Action | Authenticated User | Member | Owner |
|---|:---:|:---:|:---:|
| Create Project | ✅ (Assigned Owner role) | - | - |
| Read Project / Tasks / Member List | ❌ | ✅ | ✅ |
| Create Task | ❌ | ✅ | ✅ |
| Edit Task (including status and assignees) | ❌ | ✅ Only when assigned to the task | ✅ |
| Delete Task | ❌ | ❌ | ✅ |
| Edit / Delete Project | ❌ | ❌ | ✅ |
| Add / Remove Members | ❌ | ❌ | ✅ |
| Read / Add Comments | ❌ | ✅ | ✅ |
| List Users (for member selection), Dashboard, My Tasks | ✅ (own scope) | - | - |

### Project creation rules

- `projects.created_by` is set from the authenticated session user.
- The creator is assigned the `Owner` role. Additional selected members receive the `Member` role.
- If the creator is included in the selected members list, keep only one membership row with role `Owner` (do not overwrite with `Member`).
- Project and member records must be created within a **single database transaction**, returning success only after a complete `COMMIT`.

### Access control

- Unauthenticated request → `401 UNAUTHENTICATED`
- Non-member or non-existent project → `404 NOT_FOUND` (do not disclose whether the project exists)
- Project member with insufficient permissions → `403 FORBIDDEN`

## 6. Values, Mappings, and Validation Rules

### Status Mapping
The database preserves existing names; the API maps them to UI display labels:

| DB `status_name` | API `status` / UI Label |
|---|---|
| `To Do` | `To do` |
| `Doing` | `In progress` |
| `Done` | `Done` |

- Backend resolves `status_id` dynamically from `task_statuses` by name. Hardcoded integer status IDs are prohibited.
- New tasks default to `To Do`. The backend must supply the `status_id` explicitly (the schema has no default constraint).
- There is no fourth status called "Not started".

### Priority
The database stores `SMALLINT` (`1` = High, `2` = Medium, `3` = Low) with a `CHECK` constraint.  
API sends and receives priority as numeric values (`1 | 2 | 3`). The frontend handles localization/labeling.

### Runtime validation (src/validation.ts)

Every business route validates URL IDs, query and body with the zod schemas in `src/validation.ts`
through `parseRequest`. Bad values return 400 VALIDATION_ERROR with `details[{ field, message }]`.
Project names and descriptions, task titles and descriptions, and comments reject NUL characters.
Unknown query/body fields and repeated query keys are rejected (strict objects), so a client cannot
add `userId`, `createdBy`, `role` or `status` on create to act as someone else. Strings are trimmed
for names/titles; passwords are never touched. Pagination defaults to page 1/pageSize 10 and caps
pageSize at 50. Membership/Owner checks and the stored-date merge for PATCH are done in the routes
and database services after shape validation. TypeScript DTOs do not replace these runtime checks.

### Required Fields & Constraints

| Entity / Field | Validation Rule |
|---|---|
| Project: `projectName` | Required (maximum 150 characters) |
| Project: `startDate` | Required; defaults to current date in `Asia/Bangkok` (user editable) |
| Project: `dueDate` | Optional; if provided, must be **strictly later than** `startDate` (same date is rejected) |
| Task: `taskTitle` | Required (maximum 200 characters) |
| Task: `priority` | Required (`1`, `2`, or `3`; schema has no default) |
| Task: `dueDate` | **Required** (enforced by migration 002) |
| Task: `assigneeIds` | Required **(minimum 1 assignee)**; all assignees must belong to the project; distinct users only |
| Task: `description` | Optional |

- Every task must keep at least one assignee **in every status, including `Done`**. The last assignee cannot be removed from a task without assigning a replacement.
- Date string format must be `YYYY-MM-DD`. Malformed dates return `400 VALIDATION_ERROR`.
- *Note*: Task and membership services enforce minimum assignee count and project membership under a shared project lock.

## 7. Progress, Derived Status, and Overdue Calculation

### Project Progress
- `totalTasks` = Count of distinct `task_id` rows for the project.
- `completedTasks` = Count of tasks where status is `Done`.
- `progressPercent = ROUND(100.0 * completedTasks / totalTasks)`. If `totalTasks == 0`, return `0` (avoid division by zero).
- Examples: 4/10 = 40, 8/12 = 67. Tasks with multiple assignees are counted exactly once.
- Calculated on the fly from tasks and statuses; no separate progress column is stored.

### Derived Project Status (`derivedStatus`)
Evaluated sequentially using the following precedence rules:

| Condition | `derivedStatus` |
|---|---|
| Project has no tasks, or every task is `To Do` | `To do` |
| Project has at least 1 task, and all tasks are `Done` | `Done` |
| All other cases (contains `In progress` tasks, or mixed `To do` and `Done`) | `In progress` |

- Recalculated upon every project read. Frontend must re-fetch project details after task status updates.
- Status filters (`All`, `To do`, `In progress`, `Done`) must be validated and applied by the backend **prior** to pagination.
- Filter query parameter `GET /api/projects?status=To do|In progress|Done` (omitted returns all; URL-encode the value, e.g. `status=In%20progress`).

### Overdue Calculation (`isOverdue`)
- A task is overdue if `dueDate < today` (evaluated in `Asia/Bangkok` date comparison) **and** `status != 'Done'`. Completed tasks are never overdue.
- The API delivers `isOverdue: boolean` computed by the backend; the frontend should not duplicate this calculation.
- Dashboard metrics use all tasks in current member projects; High priority excludes Done (section 10.9).

## 8. Cascading and Deletion Policies

- **Deleting a Task** (`Owner` only): comments and `task_assignees` rows are removed by `ON DELETE CASCADE` (migration 001). A deleted task then answers `404`.
- **Deleting a Project** (`Owner` only): Tasks, assignees, comments, and project membership rows are deleted within a single database transaction (`deleteProject`; the FKs `tasks.project_id`, `project_members.project_id`, `task_assignees.task_id` and `comments.task_id` all cascade). A second `DELETE` answers `404`. The frontend must prompt for explicit confirmation before invocation. There is no soft delete or undo.
- **Removing a Member from a Project** (`Owner` only):
  - If the member is the **sole assignee of any task in the project, regardless of the task's status (including `Done`)** → Reject with `409 CONFLICT` (`reason: SOLE_ASSIGNEE`). Every task must keep at least one assignee, so completed tasks are covered too. The response lists the affected tasks.
  - If every task the member is assigned to has at least one other assignee → Remove the member from those tasks and from the project within the same transaction.
  - The last remaining `Owner` cannot be removed from the project → Reject with `409 CONFLICT` (`reason: LAST_OWNER`).
  - A user who is not a member of the project → `404 NOT_FOUND`.

## 9. Business Response Envelope and Error Codes

Applies to business endpoints only. Better Auth uses native responses/errors (section 1).

Success envelope: `{ "success": true, ... }`  
Failure envelope: `{ "success": false, "error": { "code": string, "message": string, "details"?: array } }`
For validation errors the top-level message may be generic ("Request validation failed"); details[].field and details[].message are authoritative. Clients should read details.

| HTTP Status | Error Code | Trigger Condition |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Missing or invalid fields, malformed JSON, invalid ID, invalid query parameter, unknown or repeated query key, date ordering violation |
| `413` | `VALIDATION_ERROR` | JSON body larger than 100 kB (`express.json()` limit). |
| `415` | `VALIDATION_ERROR` | Body charset or `Content-Encoding` the server cannot read |
| `401` | `UNAUTHENTICATED` | Missing or expired session cookie on a protected endpoint (business endpoints only) |
| `403` | `FORBIDDEN` | Insufficient permissions for the requested action |
| `404` | `NOT_FOUND` | Route not found, project or task not found, or user is not a project member. An unknown path under a protected prefix (e.g. `/api/tasks/123`) answers `401` first when there is no session |
| `409` | `CONFLICT` | Action violates business rules (removing a sole assignee of any task including `Done`, removing the last Owner, adding someone who is already a member) |
| `500` | `INTERNAL_ERROR` | Internal server or unhandled database exception (no stack trace leaked) |

### Error JSON Payloads

```json
// 400 Validation Error (e.g., POST /api/projects without projectName)
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Missing required fields",
    "details": [
      { "field": "projectName", "message": "projectName is required" }
    ]
  }
}

// 400 Invalid Date Range
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "dueDate must be later than startDate",
    "details": [
      { "field": "dueDate", "message": "must be later than startDate" }
    ]
  }
}

// 401 Unauthenticated (e.g., GET /api/me without valid cookie)
{
  "success": false,
  "error": {
    "code": "UNAUTHENTICATED",
    "message": "Authentication required. Please log in."
  }
}

// 403 Forbidden (e.g., Member attempting to delete a project)
{
  "success": false,
  "error": {
    "code": "FORBIDDEN",
    "message": "You do not have permission to perform this action"
  }
}

// 404 Not Found (Non-member or non-existent project)
{
  "success": false,
  "error": {
    "code": "NOT_FOUND",
    "message": "Project not found"
  }
}

// 409 Conflict (Removing a member who is the sole assignee of a task, in any status including Done)
{
  "success": false,
  "error": {
    "code": "CONFLICT",
    "message": "Member is the sole assignee of one or more tasks (including completed tasks). Reassign those tasks before removing.",
    "details": [
      { "reason": "SOLE_ASSIGNEE", "taskId": 7, "taskTitle": "Write final report", "status": "Done" }
    ]
  }
}

// 409 Conflict (Removing the last Owner)
{
  "success": false,
  "error": {
    "code": "CONFLICT",
    "message": "The last Owner cannot be removed from the project.",
    "details": [ { "reason": "LAST_OWNER" } ]
  }
}
```

## 10. Endpoint Contracts

**Conventions**
- Base path `/api`. Requests and responses are JSON.
- Business endpoints require a valid session and linked MobG user. Better Auth public routes follow library access rules; public registration is enabled with the verification policy in section 1.
- Endpoints with `:projectId` apply the access rules in section 5 (non-member or unknown project → `404`; insufficient role → `403`). A task is only reachable through the project it belongs to; a task from another project returns `404`.
- Business IDs are numbers; Auth IDs are strings. Dates are `YYYY-MM-DD`. Timestamps are ISO 8601 UTC strings.
- Status values in the API are the UI labels `To do | In progress | Done` (section 6).

```json
  "projectDescription": "Optional text",
  "startDate": "2026-10-12",
  "dueDate": "2026-12-01",
  "memberIds": [2, 3]
}

// 201
{ "success": true, "project": { "...": "project object with myRole: Owner" } }
```

- `projectName` and `startDate` required; `projectDescription`, `dueDate`, `memberIds` optional.
- Unknown user in `memberIds` → `400 VALIDATION_ERROR` with `details: [{ "field": "memberIds", ... }]`.

`GET /api/projects/:projectId` → `200` `{ "success": true, "project": { ... } }`

`PATCH /api/projects/:projectId` (Owner only; send only the fields to change)

```json
// Request
{ "projectName": "New name", "dueDate": null }

// 200
{ "success": true, "project": { "...": "updated project object" } }
```

- Editable: `projectName`, `projectDescription`, `startDate`, `dueDate`. `null` clears `projectDescription` and `dueDate`.
- At least one field is required. `dueDate` is checked against the new or existing `startDate` (section 6).

`DELETE /api/projects/:projectId` (Owner only) → `200` `{ "success": true, "message": "Project deleted" }` (cascade per section 8).

### 10.5 Members

Member object: `{ "userId": 2, "userName": "Somchai", "email": "somchai@mobg.local", "role": "Member", "joinDate": "2026-10-07" }`

`GET /api/projects/:projectId/members` → `200` `{ "success": true, "members": [ ... ] }`. Order: `Owner` first, then `userName`, then `userId`. This endpoint feeds the assignee dropdown and **must be ready in week 2**.

`POST /api/projects/:projectId/members` (Owner only)

```json
// Request
{ "userId": 4 }

// 201
{ "success": true, "member": { "userId": 4, "userName": "Malee", "email": "malee@mobg.local", "role": "Member", "joinDate": "2026-10-12" } }
```

- Unknown user → `400 VALIDATION_ERROR`. Already a member → `409 CONFLICT` (`reason: ALREADY_MEMBER`).
- This version has no endpoint to change a member's role.
- POST and DELETE recheck the caller's role after taking the project lock, in the same transaction as the write: a caller who left the project meanwhile → `404`, who is no longer Owner → `403`; nothing is written. The `201` member is built inside that transaction (a failure rolls the insert back).

`DELETE /api/projects/:projectId/members/:userId` (Owner only) → `200` `{ "success": true, "message": "Member removed" }`. Rules and `409` responses are in section 8. A user who is not a member of this project → `404 NOT_FOUND`. After removal the user immediately gets `404` on every endpoint of that project and the project's tasks leave their My Tasks and Dashboard.

### 10.6 Tasks

Task object:

```json
{
  "taskId": 1,
  "taskTitle": "Prepare database demo",
  "taskDescription": "Ensure Docker and seed data work correctly",
  "priority": 1,
  "dueDate": "2026-10-11",
  "isOverdue": false,
  "createdAt": "2026-10-07T03:20:00.000Z",
  "projectId": 1,
  "projectName": "MobG Demo Project",
  "status": "To do",
  "createdById": 1,
  "createdByName": "Demo Member",
  "assignees": [
    { "userId": 1, "userName": "Demo Member" }
  ]
}
```

`assignees` lists every assignee ordered by `userName`, then `userId`. The UI shows the first two and `+N` for the rest.

`GET /api/projects/:projectId/tasks?status=To%20do` → `200` `{ "success": true, "tasks": [ ... ] }`
- `status` optional. Order: `dueDate` ascending, then `taskId`. No pagination in this version.

`POST /api/projects/:projectId/tasks`

```json
// Request
{
  "taskTitle": "Write test plan",
  "taskDescription": "Optional text",
  "priority": 2,
  "dueDate": "2026-10-20",
  "assigneeIds": [1, 2]
}

// 201 (status starts as "To do"; createdById comes from the session)
{ "success": true, "task": { "...": "task object" } }
```

- Required: `taskTitle`, `priority`, `dueDate`, `assigneeIds`. `assigneeIds` needs at least one distinct user, and every user must be a member of the project; otherwise `400 VALIDATION_ERROR` with `details: [{ "field": "assigneeIds", ... }]`.

`GET /api/projects/:projectId/tasks/:taskId` → `200` `{ "success": true, "task": { ... } }`

`PATCH /api/projects/:projectId/tasks/:taskId` (Owner or assigned Member; send only the fields to change)

```json
// Request
{ "status": "In progress", "assigneeIds": [1, 3] }

// 200
{ "success": true, "task": { "...": "updated task object" } }
```

- Editable: `taskTitle`, `taskDescription`, `priority`, `dueDate`, `status`, `assigneeIds`.
- A project Owner may edit any task. A Member must already be assigned to that task; otherwise `403 FORBIDDEN`. Adding yourself in the request does not grant permission. The service rechecks the current role and stored assignment under the project/task locks before writing. Losing project membership still returns `404 NOT_FOUND`.
- Only a project Owner may send `assigneeIds`. A valid request from a Member that includes this field returns `403 FORBIDDEN` without applying any fields. For an Owner, `assigneeIds` replaces the whole list and follows the same rules as create. `dueDate` cannot be `null`.
- After a status change the frontend must re-fetch the project (`derivedStatus` and `progressPercent` change).

`DELETE /api/projects/:projectId/tasks/:taskId` (Owner only) → `200` `{ "success": true, "message": "Task deleted" }`

`GET /api/tasks/mine?status=Done` → `200` `{ "success": true, "tasks": [ ... ] }`
- Tasks assigned to the current user across all projects. Same task object (includes `projectId` and `projectName`). Order: `dueDate` ascending, then `taskId`.
- The user is always the session user. Only a task the user is assigned to **and** whose project the user is still an `Owner`/`Member` of is returned; each task appears once.
- Query: only optional `status` (`To do` / `In progress` / `Done`). No query → every such task. Any other key (`userId`, `projectId`, `q`, `priority`, `page`, …), an unknown status, or a repeated `status` → `400 VALIDATION_ERROR`. No match or no assigned tasks → `200` with `tasks: []`.

### 10.7 Comments

Comment object: `{ "commentId": 5, "commentText": "Looks good", "createdAt": "2026-10-08T09:00:00.000Z", "userId": 1, "userName": "Demo Member" }`

`GET .../tasks/:taskId/comments` → `200` `{ "success": true, "comments": [ ... ] }` (oldest first)

`POST .../tasks/:taskId/comments`

```json
// Request
{ "commentText": "Looks good" }

// 201
{ "success": true, "comment": { "...": "comment object" } }
```

`commentText` is required and must not be empty after trimming. The author is the session user.

Both endpoints are implemented. Any current project `Owner` or `Member` can read and add comments,
including on tasks created by or assigned to someone else. The task must belong to the project in
the URL. Anonymous or expired sessions receive `401`; non-members, missing tasks and cross-project
task IDs receive `404`. Unknown body fields (including a forged `userId`) receive `400`.
Comments are ordered by creation time, then comment ID ascending. Creation rechecks membership
under the project lock so removal while waiting cannot result in a new comment.
The task detail page displays persisted comments, author names and timestamps and includes a comment form.

### 10.9 Dashboard

`GET /api/dashboard?limit=5` → `200`

```json
{
  "success": true,
  "summary": {
    "projectCount": 3,
    "taskCount": 25,
    "statusCounts": { "todo": 10, "inProgress": 6, "done": 9 },
    "overdueCount": 2,
    "highPriorityCount": 5
  },

```

- Query: only optional `limit` (integer 1–100, default `5`) for the length of `highPriorityTasks`; it does not change `summary`. Any other key (such as `userId`), a non-integer or out-of-range `limit`, or a repeated `limit` → `400 VALIDATION_ERROR`.
- A user with no projects gets every count `0` and `highPriorityTasks: []`.
- `summary` and `highPriorityTasks` are read by two queries, not one snapshot; they can differ only if data changes between them.

- Scope: projects the current user belongs to. Each distinct task is counted once.
- `highPriorityCount` and `highPriorityTasks` use `priority = 1` and status not `Done`. `highPriorityTasks` is ordered by `due_date` and `task_id` ascending, with a default limit of 5 and an allowed range of 1–100.
- The Dashboard UI's Important Tasks panel uses `GET /api/tasks/mine` and displays up to five of the current user's open assignments across all priorities.
- DB implementations: `getDashboardSummary(user_id)` in `services/dashboardDb.ts`, `listHighPriorityTasks(user_id, limit = 5)` in `services/taskDb.ts`. Both use current membership scope, without assignee joins multiplying task counts.

### 10.10 Topbar search

`GET /api/search?q=keyword` returns up to eight projects and eight tasks from
projects where the current user is an Owner or Member. The trimmed query must
contain 1–200 characters. It matches literal substrings of project names or task
titles, case-insensitively. Results are ordered by name or title, then by ID.

```json
{
  "success": true,
  "projects": [{ "projectId": 2, "projectName": "Design" }],
  "tasks": [{ "taskId": 7, "taskTitle": "Design login", "projectId": 2, "projectName": "Design" }]
}
```

No matches return empty arrays. Invalid queries return `400`. Missing sessions
return `401` and sessions without linked MobG profiles return `403`.

## 11. Database Function Contracts for Feature Endpoints

**Conventions**
- Inputs with several values are passed as one object. All IDs are numbers.
- Rows are returned in `snake_case`. `BIGINT` values stay decimal strings in database results; the backend converts them to numbers only after the safe-integer check and maps names to `camelCase` (section 4, ID Boundaries). `COUNT` values may also arrive as strings.
- `null` means "not found". Database errors are re-thrown. Failed foreign keys and duplicate keys are re-thrown as is, so the backend can map them to `400` or `409`.
- Task `status_name` uses the database names `To Do | Doing | Done`. Project `derived_status` uses the UI labels `To do | In progress | Done` because it is not stored. The backend maps `status_name` to the UI label.
- Functions that change several tables run in one transaction on one connection.
- Dates are compared in `Asia/Bangkok` (section 7).

### 11.1 Users and projects

| Function | Input | Output |
|---|---|---|
| `listUsers()` | none | `[{ user_id, user_name, email }]` ordered by `user_name`, `user_id` |
| `listProjectsForUser({ user_id, status, page, page_size })` | `status`: `null` or `'To do' \| 'In progress' \| 'Done'` (filter applied before paging) | `{ items: [project], total_items }` newest first, where `project` = `{ project_id, project_name, project_description, start_date, due_date, project_create_date, created_by, creator_name, my_role, total_tasks, completed_tasks, progress_percent, derived_status }` |
| `getProjectById(project_id)` | project id | `project` without `my_role`, or `null` |
| `createProjectWithMembers({ project_name, project_description, start_date, due_date, created_by, member_ids })` | `member_ids`: array of ids, may be empty | `{ project_id }`. Creator gets `Owner`, others `Member`, creator is not duplicated; one transaction. An unknown id in `member_ids` throws a foreign key error. |
| `updateProject(project_id, changes)` | `changes`: any of `project_name`, `project_description`, `start_date`, `due_date` | `true` if the project exists, else `false` |
| `deleteProject(project_id)` | project id | `true` if deleted, else `false`. Removes comments, assignees, tasks, memberships, and the project in one transaction. |

### 11.2 Members

| Function | Input | Output |
|---|---|---|
| `listProjectMembers(project_id)` | project id | `[{ user_id, user_name, email, role, date_join }]`, `Owner` first, then `user_name`, `user_id` |
| `addProjectMember({ project_id, actor_user_id, user_id }, prepare)` | ids; `prepare(row)` maps `{ user_id, user_name, email, role, date_join }` | Locks the project, then requires `actor_user_id` to be an Owner in the same transaction: `{ added: false, reason: 'ACTOR_NOT_MEMBER' \| 'ACTOR_NOT_OWNER' }`. Otherwise inserts a `Member` and returns `{ added: true, member: prepare(row) }`, computed before COMMIT (a throwing `prepare` rolls back). Duplicate or unknown user throws a key error. |
| `removeProjectMember({ project_id, actor_user_id, user_id })` | ids | Same actor check under the project lock (`ACTOR_NOT_MEMBER`, `ACTOR_NOT_OWNER`). Then `{ removed: true }` or `{ removed: false, reason }` where `reason` is `NOT_MEMBER`, `LAST_OWNER`, or `SOLE_ASSIGNEE` (the last one also returns `tasks: [{ task_id, task_title, status_name }]`). The sole-assignee check covers tasks in every status including `Done`. On success it removes the user from the project's `task_assignees` rows and from `project_members` in one transaction. |

### 11.3 Tasks

The task services are in `src/services/taskDb.ts` and the HTTP routes are in
`src/routes/tasks.ts`.

Before calling update/delete by task ID, the backend must check the role and use
`getTaskById(project_id, task_id)` to reject a task belonging to another project.
Omitted/undefined PATCH fields stay unchanged; only `task_description` accepts null.
Backend validates membership and minimum assignees first. Task creation and updates also recheck these inside the transaction under a shared project lock, coordinating with member add/remove. A stale membership or empty set throws `InvalidTaskAssigneesError`; existing task routes map it to 400 `VALIDATION_ERROR`. Native database errors still propagate.

`task` row: `{ task_id, task_title, task_description, priority, due_date, task_create_date, project_id, project_name, status_name, is_overdue, created_by, created_by_name, assignees: [{ user_id, user_name }] }` with `assignees` ordered by `user_name`, `user_id`.

| Function | Input | Output |
|---|---|---|
| `listTasksByProject({ project_id, status_name })` | `status_name`: `null` or `'To Do' \| 'Doing' \| 'Done'` | `[task]` ordered by `due_date`, `task_id` |
| `getTaskById(project_id, task_id)` | ids | `task`, or `null` if the task does not exist **in that project** |
| `listTasksForAssignee({ user_id, status_name })` | as above | `[task]` ordered by `due_date`, `task_id` |
| `listHighPriorityTasks(user_id, limit = 5)` | linked session MobG ID; limit integer 1–100 | `[task]` in current member projects, priority 1, excluding Done; ordered by `due_date`, `task_id`, then limited |
| `createTask({ project_id, task_title, task_description, priority, due_date, created_by, assignee_ids })` | `assignee_ids`: array of ids | `{ task_id }`. Resolves the `To Do` `status_id` by name; inserts the task and its assignees in one transaction. The backend validates membership and the minimum of one assignee first (section 6). After taking the project lock, `created_by` must still be Owner/Member in the same transaction; otherwise it throws `TaskCreatorNotMemberError`, nothing is written, and POST answers `404`. |
| `updateTask(task_id, changes, actor?)` | `changes`: any of `task_title`, `task_description`, `priority`, `due_date`, `status_name`, `assignee_ids`; optional `actor: { project_id, user_id }` | `true` if updated, else `false` for a missing task, wrong project, or lost membership (PATCH → `404`). With `actor` (the PATCH route always passes it), the service rechecks authorization under project/task locks. An Owner can edit all fields, and a current assignee can edit fields other than `assignee_ids`. Unauthorized edits throw `TaskEditForbiddenError` (PATCH → `403`) before writing. `status_name` is resolved to `status_id` by name. `assignee_ids` replaces the whole set. Omitting `actor` is reserved for trusted internal callers. |
| `deleteTask(task_id)` | task id | `true` if deleted, else `false`. Removes `task_assignees` rows and the task; comments are removed by `ON DELETE CASCADE`. |

`is_overdue` = `due_date` is before today in `Asia/Bangkok` and `status_name` is not `Done`.

My Tasks requires both assignment and current project membership with role Owner or Member; unknown roles grant no access. Dashboard counts and important tasks use the same role whitelist. My Tasks accepts only the optional `status` filter.
Member add/remove implementations live in `projectDb.ts`; rejection task lists are ordered by `task_id` ascending.
